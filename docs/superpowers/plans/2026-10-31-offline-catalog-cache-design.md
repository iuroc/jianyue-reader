# 离线书刊库（缓存方案 B）· 设计草案

状态：**下一期开发方案，本期不实施**
日期：2026-10-31
关联：`openspec/changes/jianyue-reader/`（本期变更，不做缓存）

## 为什么现在不做

本期先把「浏览 → 详情 → 阅读 → 搜索」跑通并验收。缓存属于架构级改动，
会同时影响列表页、搜索、索引器三个模块，放在功能稳定之后单独做一期更安全。

## 服务端事实（2026-10-31 实测）

```
Cache-Control: no-cache
Expires: Thu, 01 Jan 1970 00:00:00 GMT
无 ETag、无 Last-Modified
```

结论：**没有条件请求可用**，缓存必须在客户端自己实现，不能依赖 HTTP 缓存层。

## 数据分五类

| 数据 | 变化频率 | 体积 | 建议策略 |
|---|---|---|---|
| 图书/期刊列表 | 月级 | 原始 JSON ≈ 9 MB | 落成本地库，见下 |
| 期刊期次 | 月级 | 每刊几十条 | TTL 1 天 |
| token（sid/from/detailUrl） | 未知，可能短期失效 | 1 KB | TTL 12 小时，失败即失效 |
| 目录 | 基本不变 | 1–3 KB/本 | 永久 |
| 正文段 | 基本不变 | 100–250 KB/段 | 永久 + LRU 50 MB |

## 方案：统一成本地书刊库

把现在分散的两套数据合并成一份：

```
18 个分类各抓一次（pageSize=-1）
        |
        v
  本地书刊库（全字段，精简落盘 ~1 MB）
   ├─ 图书 Tab：直接读本地，加载更多 = 本地翻页
   ├─ 期刊 Tab：同上
   └─ 搜索：读同一份，不再有「先建索引」这一步
```

### 与当前实现的差异

| 项 | 现在 | 方案 B |
|---|---|---|
| 列表数据 | 每次翻页请求服务器 | 首次同步后全部本地 |
| 加载更多 | 向服务器要下一页 | 从本地翻下一页 |
| 搜索 | 单独建索引（18 个分片） | 与列表库同一份，无需单独建 |
| 首屏 | 每页一次请求 | 首次一次性同步（约 9 MB 下载） |
| 离线 | 不可浏览 | 可浏览、可搜索 |

### 加载按钮的状态可以简化

本地翻页后，「载入中」「失败重试」基本不会出现，四态可收敛为两态
（可加载 / 已到底）。规格里「固定高度防抖动」依然有效。

## 正文与目录

```
正文段   键 = surl + w/h/fsize + start    永不过期，LRU，总容量上限 50 MB
目录     键 = surl + w/h/fsize            永不过期（每本 1–3 KB）
```

需要一份 `cache_index.json` 记录每个文件的 `key / size / lastAccess`，
写入前检查总大小，超限按最后访问时间淘汰。

一本 84 页的书约 2–3 MB，50 MB 约能存十几本。

## token 是唯一有风险的缓存

`sid` / `from` / `detailUrl` 有效期未验证（skill 标 ❓）。

```
缓存 12 小时
正文或目录返回 result:0  ->  立即作废 token，重取一次
连续失败两次             ->  报「打开失败」
```

不能永久缓存，否则某天集体失效时全部打不开。

## 待定参数

- 缓存总容量上限（暂定 50 MB）
- 是否提供「手动刷新书刊库」入口
- 「我的」里是否展示缓存占用 + 清空（倾向要，成本低）

## 并发去重

同一页被两个线程同时请求时，只发一次、其余等结果。
现在索引器是 4 线程并发的，不做去重会出现重复请求。

## 落地顺序建议

1. 本地库的读写与同步（18 个分类、单文件、精简字段）
2. 列表页改读本地库，加载更多改本地翻页
3. 搜索改读同一份，删掉独立的索引器
4. 目录与正文的分层缓存 + LRU
5. token 失效处理与刷新入口
